# GSuite Signature Management

## Workspace

Each user has one membership, and that membership is the customer they can access. The customer link stores the primary domain and the Workspace admin email. Directory calls impersonate that admin. Signature updates impersonate each mailbox. The API resolves the customer from the membership because it writes with the Admin SDK.

## Data

Wizard Save goes through the API, which writes templates and assignments in Firestore and enqueues one signature deploy. That job reads the template once and the directory once, sets each signature in-process, and writes one deploy log when it finishes. People, groups, and OUs for assignment come from the Workspace Directory API (`GET /api/directory`); local/dev uses the mock Directory client seeded with fixtures.

## Signatures

Signature fonts are inline font stacks. Gmail and Outlook strip `@font-face`.

The rich text editor uses TinyMCE's oxide skin. That skin is what makes the canvas visible after init.

## Runtime

Client Firebase config is the `VITE_*` variables Vite loads from `packages/.env` (see `packages/.env.example`), via the frontend Vite config. The local API and seed script read `VITE_FIREBASE_PROJECT_ID` from that same file. Emulators and deploy use the project id in `.firebaserc`. Deploy passes `--project default` so that alias wins over a previously selected project on this directory. Those two ids have to match. `yarn dev` starts Auth/Firestore emulators, a local API server on port 3000, and Vite together. Vite proxies `/api` to that API process.

The default emulator command imports the firebase package seed and writes it back on exit, so a dev session rewrites that seed.

Cloud Functions and the shared package entry are compiled output. The frontend resolves shared from source, so `dev:all` is what rebuilds both during a session.

Yarn uses the node-modules linker. Plug'n'Play breaks Vite and the Functions emulator.

`yarn dev` loads the frontend Vite config. That config and TypeScript resolve `@/functions` to the functions package; the repo-root Vite config does not.

The Firestore database id is `default`. The client libraries and the CLI use `(default)` unless that id is set. The emulator still uses `(default)`. The Firebase CLI's project directory is the repo root, where `firebase.json` and `.firebaserc` live. Functions source and the Hosting build have to stay inside that directory. Production serves the admin UI from Firebase Hosting and rewrites `/api` to a Cloud Function in the same project. Client Firestore access is authorized by the security rules deployed with the app. The API uses the Admin SDK and bypasses those rules. Signature deploy jobs use Cloud Tasks. Local/dev uses a Node HTTP API with an inline queue publisher and a mock Gmail client until the real Gmail client is configured.
